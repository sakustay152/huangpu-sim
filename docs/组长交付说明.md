## 2. 冻结接口一览（改接口需全组同意）

```cpp
IScreen       { id(); onEnter(); render(); handleInput(string); isModal(); }
ISaveable     { toJson(); fromJson(Json); }
IPriceModel   { double price(const PriceContext&); }          // B 实现因子链
IEvent        { bool canTrigger(ctx); void apply(ctx); }       // D 实现 GameEvent 树
IEffect       { string apply(ctx); int estimateMoneyDelta(); } // D 实现，模拟器依赖估算
ICondition    { bool test(ctx); }                              // D 实现，事件+结局两处复用
ICommand      { name(); ActionResult execute(ctx); }           // C 实现各行动
ITimeListener { onDayTick(); onWeekStart(); }                  // Market 已实现
```

**两条铁律**：
1. `GameContext` 是唯一组合点 —— 各系统互相不 include 头文件，只通过 `GameContext` 访问彼此（前向声明），杜绝循环依赖。
2. 屏幕层只调 `Game` 的公共方法（performAction/requestEndWeek/saveGame…），不直接改系统内部状态 —— E 的 SFML 屏幕实现同一套 `IScreen` 即可整体替换控制台 UI。

**答辩可能被问的三个"为什么"**：
1. *为什么价格用策略+装饰器而不是一个公式？* 因子可独立单测、可按商品开关、新增因子（如节假日）不改旧代码；模拟器发现某因子失衡时可以单独关掉验证。
2. *为什么事件效果数据化（JSON）而不写代码？* 内容产出（D）与机制（A）解耦；改文案/数值不重编译；EventFactory 在启动时校验所有引用，坏数据活不过启动。
3. *模拟器怎么用的？* 见下一节真实校准记录 —— 它不是摆设，目标金额和限购都是它调出来的。

## 5. 数值校准记录（分工 8.9 流程的实证）

流程：改 `data/*.json` → `huangpu_simulate.exe --simulate 1000 --seed 42` → 看结局分布 → 再提交。**全程未改游戏逻辑代码**（数据驱动的设计红利）。

| 轮 | 关键改动 | trader | worker | mixed | 结论 |
| --- | --- | --- | --- | --- | --- |
| 1 | 初始锚点（目标 12000、限购按周） | 5067 | 6396 | 5396 | 三策略全失败；打工 > 倒卖，倒卖无吸引力 |
| 2 | 限购改"每地点每日"（对齐分工 3.4）；价差拉大 | 8108 | 6396 | 7281 | 倒卖反超打工；但结局判定漏算库存估值 |
| 3 | 新增 `totalAssetsMin`（现金+库存估值）；Bot 修正学业/社交策略 | 15032 | 5668 | 12388 | 矫枉过正，99.4% 好结局 |
| 4 | 回调高价商品限额/系数；目标 12000→7500 | 9282 | 5668 | **7720** | ✅ mixed 53.7% 站稳脚跟；trader 钱最多但 0% 好结局；worker 不达标 |

最终形态印证设计目标：**"只倒卖"赚最多但孤独、**"只打工"安稳但失败、**混合策略**才是好结局路径，不存在单一最优解。
